# 📜 REGRAS DE OURO — PROTOCOLO DE BLINDAGEM (Projeto Enki)

> Documento **constitucional** do projeto Enki. Toda Ordem de Serviço
> (`prompt.md` + templates de `docs/templates/`) é interpretada SOB
> estas regras. Em qualquer conflito, **este documento prevalece**.
>
> **Glossário:**
> - **Antigravity** = agente de codificação assistido por IA utilizado
>   como desenvolvedor neste projeto.
> - **Oráculo** = LLM externa de validação que gera Ordens de Serviço
>   parametrizadas a partir de briefings do Product Owner.
> - **Product Owner** = Aristóteles Soares Benício.

---

## §0. MANIFESTO (4 PILARES)

### §0.1. Privacidade por Padrão (ISO 27001)
- Toda interface é construída assumindo **ambiente do cliente hostil**.
- **Isolamento de Contexto:** temas, permissões e dados sensíveis são
  injetados via *Scoped Variables*. O visual de um Board "Escriba"
  nunca vaza para o contexto global.

### §0.2. Transparência e Ética Algorítmica (ISO 42001)
- Interfaces que usam IA devem expor **estado de processamento** e
  **origem dos dados**.
- Proibidas "alucinações de UI" e Layout Shifts não documentados.

### §0.3. Arquitetura "Rigid Shell"
- **Proibido transbordamento de viewport.** Layout = grid fixo e
  previsível.
- Scroll é recurso **local e controlado**. Eliminam-se vulnerabilidades
  de overlap e bugs de "tela branca".

### §0.4. Acessibilidade por Padrão
- **WCAG 2.2 AA** é o piso mínimo, validado em pipeline de CI.

---

## §1. 🏗️ ARQUITETURA DE INTERFACE (RIGID SHELL)

### §1.1. Morte ao `100vh` / `100vw` em containers internos
- Usar `dvh` (Dynamic Viewport Height) para compatibilidade Safari/iOS.
- Usar `svh` para telas fixas.
- Usar `lvh` apenas com justificativa documentada via `[PROVENANCE]`.

### §1.2. Viewport Lockdown
- `root` e `body` com `overflow: hidden`.
- Scroll permitido APENAS em containers `.pt-scroll-area` via CSS Grid.

### §1.3. PWA Mobile-First (macOS/iOS)
- `padding: env(safe-area-inset-*)` obrigatório (notches).
- `touch-action: pan-x pan-y` em áreas de scroll (evita "bounce"
  elástico que quebra Drag-and-Drop).

### §1.4. Isolamento de Temas (Scoped CSS)
- **Proibidas** classes globais de tema no `body`.
- Usar `data-theme="scribe"` ou `style={{ '--accent': ... }}` no
  container raiz do Board.

### §1.5. Skeletons (Layout Shift)
- Reservar espaço exato da UI final em Kanban / Tabela / Calendário.
- **Métrica:** CLS < 0.05 nas três visões.

### §1.6. Estética "Precision Tech"
- Densidade de informação alta.
- **Tipografia mono canônica:** `JetBrains Mono` como família
  primária; fallback: `ui-monospace, SFMono-Regular, "SF Mono",
  Menlo, Consolas, monospace`.
- Feedback visual imediato em escritas no Firestore.

> 📌 **Nota constitucional:** o token canônico foi fixado nesta
> revisão (v1.1) para remover débito anterior. Mudanças exigem ADR
> em `docs/governance/`.

---

## §2. 🔐 SEGURANÇA DE APLICAÇÃO

### §2.1. Shadow Logic (Espelhamento Frontend ↔ Firestore Rules)
- **Anti-Frontend-Security:** proibido confiar apenas em `if(user)`
  no React.
- Toda lógica de permissão **DEVE** ter regra equivalente em
  `firestore.rules`.
- **Database Rejection:** o banco rejeita leituras quando o UID não
  está em `board.members[]` (ou campo canônico equivalente no schema
  Enki).

### §2.2. Sanitização & Anti-XSS
- Todo input do usuário é tratado como **dado radioativo**.
- Sanitização **obrigatória via `DOMPurify`** (ou biblioteca auditada
  equivalente) antes de renderização no DOM.
- **Proibida** sanitização via regex manual.
- Aplicação sistemática em títulos, descrições e qualquer campo livre.

### §2.3. Data Leakage (Selectors Mínimos)
- Auditar selectors: buscar APENAS o campo necessário.
  - ✅ `useUserPhotoURL(uid)`
  - ❌ `useUser(uid).photoURL`
- E-mails e metadados internos **não podem** vazar ao frontend.

### §2.4. Política de Segredos
- **Proibido** segredo no client bundle (`process.env.*` exposto,
  chaves em código, tokens em `localStorage`).
- Usar **Firebase App Check** + variáveis server-side / Cloud Functions.

---

## §3. 🏗️ ZERO-TRUST TYPESCRIPT

### §3.1. Uso de `any` = falha de segurança **Crítica** (dívida técnica).
### §3.2. Uso de `unknown` sem narrowing explícito = severidade **Alta**.
### §3.3. Proibidos `@ts-ignore` e `@ts-expect-error` sem justificativa em comentário e ticket no `BACKLOG.md`.
### §3.4. Tipos genéricos/inconsistentes herdados → **refatoração imediata** para interfaces estritas.
### §3.5. Funções exportadas devem ter **tipo de retorno explícito**.

---

## §4. 🚮 HIGIENE DE AMBIENTE (Migração Windows → macOS)

### §4.1. Anti-Metadata
- Ignorar/remover `Thumbs.db`, `desktop.ini`, `.DS_Store`,
  `.AppleDouble`, `._*`, `Icon?` e caminhos `C:\`.

### §4.2. Line Endings
- Forçar `LF` (Unix) em todos os novos arquivos
  (`.gitattributes` com `* text=auto eol=lf`).

### §4.3. Git Identity
- Novos commits usam apenas configuração `--local` do repositório
  (nunca `--global`).

---

## §5. 🧠 COMANDO DE DESCONFIANÇA (Security Engineer Mode)

Antes de QUALQUER tarefa de backlog, o agente assume a persona de
**Security Engineer** e executa varredura prévia em:

- `src/services/` (em especial `cardService`, `boardService`,
  `userService`)
- `src/hooks/`
- `src/context/`
- `src/pages/`

**Vetores obrigatórios de verificação:**
1. Shadow Logic (§2.1)
2. XSS / Sanitização (§2.2)
3. Data Leakage (§2.3)
4. Tipagem tênue / `any` / `unknown` (§3)
5. Vazamento de segredos (§2.4)

A varredura é **recursiva** e cobre todos os subdiretórios.

## §8. 🧠 PROTOCOLO ANTI-VIBE-CODING (ISO 42001)

> "Vibe coding" = aceitar sugestão da LLM porque "soa certo", sem
> verificação contra a stack atual, documentação oficial e contexto
> do projeto. É considerado **falha de governança de IA**.

### §8.1. Princípio da Suspeita Reversa
A IA é tratada como **estagiário talentoso porém desatualizado**.
Toda sugestão é considerada "potencialmente herdada de corpus
obsoleto" até prova em contrário.

### §8.2. Proibições Explícitas (Padrões Mortos)
Proibida a introdução de:
- `var` (usar `const`/`let`)
- Class components React em código novo (preferir function + hooks)
- `componentWillMount`, `componentWillReceiveProps`, e outros
  lifecycles legados
- Callbacks aninhados quando `async/await` resolve
- `moment.js` (usar `date-fns` ou `Temporal` API)
- `request`, `request-promise` (usar `fetch` nativo ou `undici`)
- `node-sass` (usar `sass` / `dart-sass`)
- `enzyme` em testes novos (usar `@testing-library`)
- jQuery em qualquer hipótese

### §8.3. Verificação de Atualidade da Stack
Antes de sugerir qualquer biblioteca, o agente DEVE:
1. Verificar `package.json` para versões reais instaladas.
2. Confirmar que a API sugerida existe na versão instalada
   (não em versão imaginada).
3. Em caso de dúvida sobre API: declarar a dúvida em vez de
   gerar código "plausível" (ver §9).

### §8.4. Anti-Slopsquatting (Dependências Fantasma)
- **Proibido** sugerir pacote npm sem confirmação de existência real.
- Toda nova dependência exige:
  - Link para o registro npm/GitHub oficial.
  - Verificação de manutenção ativa (último commit < 12 meses).
  - Análise de superfície de ataque (downloads semanais > 10k OU
    auditoria manual documentada).

### §8.5. Detecção de Antipadrões Memorizados
Sinalizar e refatorar quando encontrar:
- `try/catch` que engole erro silenciosamente
- `JSON.parse` sem `try/catch` ou schema (Zod/Valibot)
- Regex caseiro para e-mail, URL, CPF (usar libs auditadas)
- `innerHTML` (usar `textContent` ou framework)
- `eval`, `Function()` constructor, `setTimeout(string, ...)`
- JWT/tokens em `localStorage` (usar httpOnly cookies)
- `Math.random()` para qualquer uso security-sensitive
- Comparação de string com timing attack (`===` em senha/token)

### §8.6. Cargo Cult Hooks (React-específico)
Sinalizar uso desnecessário de:
- `useEffect` para sincronizar estado derivado (preferir cálculo direto)
- `useMemo`/`useCallback` sem profiling que justifique
- `useState` para valor que poderia ser ref ou constante
- `useRef` para valor que poderia ser `useState`

### §8.7. Provenance Obrigatória
Toda decisão arquitetural não-óbvia introduzida pelo Antigravity
DEVE vir com comentário no formato:

```ts
// [PROVENANCE] <razão> | <fonte> | <data>
// ex.: [PROVENANCE] React 19 use() preferred over useEffect for data fetching
//      | https://react.dev/reference/react/use | 2026-06
```

### §8.8. "Idiomatic Check" Antes do Commit
Para a stack declarada (Tailwind v4 / React 19 / TS 5.x / Vite atual):
- O código gerado segue a documentação OFICIAL da versão instalada?
- Há padrão mais idiomático introduzido na major recente?
- Em caso de dúvida: marcar com `// TODO: idiomatic-review` em vez de
  commitar "no feeling".

---

## §9. 🤔 PRINCÍPIO DO "NÃO SEI" HONESTO

> Promovido de §8.9 da v1.0 para regra estrutural na v1.1.

### §9.1. Declaração de incerteza é preferível a fabricação
A IA DEVE preferir declarar incerteza a fabricar plausibilidade.

**Frase canônica aceita:**
> *"Não tenho certeza se esta API existe nesta versão — favor
> confirmar na documentação oficial."*

**Saída proibida:** gerar código "plausível" sem ancoragem verificável.

### §9.2. Canal de captura de incerteza
Quando o agente declara incerteza durante uma OS, ele DEVE:
1. Marcar o ponto com `// TODO: provenance-pending` no código.
2. Registrar a pergunta em aberto no Gate humano da OS.
3. Aguardar decisão do Product Owner antes de prosseguir.

### §9.3. "Hipóteses Assumidas" são primeira-classe
Toda OS pode (e deve, quando aplicável) declarar bloco
`LISTA_HIPOTESES` no briefing. Hipóteses não declaradas são
consideradas inexistentes — Antigravity NÃO assume tacitamente.

# 📐 PROTOCOLO DE ORDENS DE SERVIÇO PARAMETRIZADAS — Projeto Enki

> Este documento define o **protocolo permanente** de geração,
> materialização e execução de Ordens de Serviço (OSs) no projeto
> Enki. Ele é executado SOB as Regras de Ouro do `cursorrules.md`
> (v1.1 ou superior).
>
> Em qualquer conflito, vale a Hierarquia de Autoridade definida em
> `cursorrules.md §10`.

---

## 1. 🎯 PROPÓSITO

Padronizar o ciclo completo de uma OS no Enki, de modo que:

- Todo pedido do Product Owner gere uma OS **rastreável e auditável**.
- O Antigravity execute apenas instruções **resolvidas, validadas e
  ancoradas** no `cursorrules.md`.
- Nenhum placeholder Mustache vaze para o repositório.
- Nenhuma decisão "plausível" sem `[PROVENANCE]` seja aceita
  (cursorrules §8.7 + §9).

---

## 2. 🧭 FLUXO CANÔNICO DA OS

```
┌─────────────────────────────────────────┐
│ 1. Product Owner preenche briefing      │
│    docs/REQUEST-OS-TEMPLATE.md          │
└─────────────────────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────┐
│ 2. Oráculo recebe briefing e responde   │
│    com Bloco A (parâmetros) +           │
│    Bloco B (instrução de materialização)│
└─────────────────────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────┐
│ 3. Product Owner revisa Bloco A         │
│    (corrige se necessário) e aprova     │
└─────────────────────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────┐
│ 4. Antigravity:                         │
│    a. Localiza template em              │
│       docs/templates/                   │
│    b. Renderiza via mustache.js v4.x    │
│    c. Valida (regex + engine)           │
│    d. Salva em docs/orders/             │
│    e. Executa, parando nos Gates        │
└─────────────────────────────────────────┘
                  │
                  ▼

│ 5. DoD verificada → OS [EXECUTADA]      │
│    + commit/tag conforme aplicável      │
└─────────────────────────────────────────┘
```

## 3. 🔧 ENGINE MUSTACHE OFICIAL

### 3.1. Engine canônico
- **Implementação:** [`mustache.js`](https://github.com/janl/mustache.js)
  versão `^4.2.0`.
- **Justificativa:** padrão de mercado, manutenção ativa, sem
  dependências, especificação Mustache 1.4 completa.
- **Alternativa permitida:** apenas se documentada via ADR em
  `docs/governance/`.

### 3.2. Sintaxe oficial de placeholders

| Tipo | Sintaxe | Renderização |
|---|---|---|
| Simples | `{{NOME_PARAMETRO}}` | substituído por valor único |
| Lista (seção positiva) | `{{#LISTA_NOME}}...{{/LISTA_NOME}}` | repetido por item |
| Condicional positiva | `{{#IF_X}}...{{/IF_X}}` | incluído se truthy |
| Condicional negativa | `{{^IF_X}}...{{/IF_X}}` | incluído se falsy |
| Comentário | `{{! texto }}` | renderizado como vazio |

### 3.3. Convenção de nomenclatura
- **Variáveis simples:** `UPPER_SNAKE_CASE` (ex.: `TITULO_OS`).
- **Listas:** prefixo `LISTA_` (ex.: `LISTA_INCLUI`).
- **Flags booleanas:** prefixo `IF_` (ex.: `IF_TOCA_FIRESTORE_RULES`).

---

## 4. 🛡️ VALIDAÇÃO DE PLACEHOLDERS (REGRA INVIOLÁVEL)

### 4.1. Após renderização pelo engine

Antes de salvar QUALQUER OS materializada em `docs/orders/`, o
Antigravity DEVE executar a sequência abaixo **na ordem**:

#### Passo 1 — Validação de parâmetros não-resolvidos

Aplicar a regex:

```regex
\{\{(?![!#/^])[^}]+\}\}
```

> 📌 **Por que esta regex e não a anterior:**
> - `(?![!#/^])` = lookahead negativo que ignora **comentários**
>   (`{{!}}`), **aberturas** (`{{#}}`), **fechamentos** (`{{/}}`) e
>   **inversões** (`{{^}}`).
> - Captura **apenas** placeholders simples não-resolvidos
>   (`{{NOME}}`).
> - Resolve o falso-positivo que existia na regex `\{\{[^}]+\}\}`
>   da v1.0.

Se houver QUALQUER ocorrência:
- **ABORTAR** imediatamente.
- **NÃO SALVAR** o arquivo.
- Reportar no chat:
  - Quantidade de placeholders pendentes.
  - Lista exata de cada um.
  - Linha onde aparecem.
- Aguardar nova OS corrigida.

#### Passo 2 — Validação de seções remanescentes

Aplicar a regex:

```regex
\{\{[#/^][^}]+\}\}
```

Se houver QUALQUER ocorrência:
- **ABORTAR** com mensagem específica:
  > *"Falha de engine Mustache: aberturas/fechamentos de seção
  > remanescentes. Verificar se o engine `mustache.js` foi invocado
  > corretamente, ou se a OS forneceu o array/flag esperado."*
- Esta falha é **diferente** da anterior: indica que o **engine**
  falhou, não que o **parâmetro** está faltando.

#### Passo 3 — Confirmação positiva

Se ambas as regex retornarem zero ocorrências:
- Salvar o arquivo materializado.
- Prosseguir com a execução da OS.

### 4.2. Auto-validação adicional

Além das regex acima, o Antigravity DEVE verificar:

- **Consistência de listas:** se um template usa `{{#LISTA_X}}` mas
  o parâmetro `LISTA_X` não foi fornecido, abortar.
- **Tipos esperados:** se um parâmetro deveria ser data UTC e veio em
  outro formato, abortar.
- **Caminhos de arquivo:** se a OS referencia caminhos que não existem
  e não estão na lista de `LISTA_ARQUIVOS_CRIAR`, abortar.
- **Coerência de versão:** `CURSORRULES_VERSAO_LIDA` deve ser
  compatível com a versão do `cursorrules.md` no momento da execução.

> Esta camada impede que arquivos com `{{XYZ}}` literal vazem para o
> repositório, o que constituiria falha de governança ISO 27001/42001.

# Diagnóstico Clínico da Interface (UI/UX)

## 1.1 Viewport Toxicity
Foram encontrados usos de classes utilitárias e estilos que forçam o uso integral da viewport, o que é a principal causa do scroll lateral indesejado (especialmente no Safari/macOS devido à barra de rolagem sobreposta) e das quebras de layout em dispositivos móveis (por causa das barras de navegação).

| Caminho | Linha | Token | Contexto | Impacto Safari/iOS |
| :--- | :--- | :--- | :--- | :--- |
| `src/pages/AdminPanel.tsx` | 85, 90, 112 | `min-h-screen` | Container principal do painel | Scroll indesejado no mobile devido à safe-area. |
| `src/pages/Profile.tsx` | 68, 76, 88 | `min-h-screen` | Layout principal do perfil | Extensão da altura além da viewport real em iOS. |
| `src/pages/Login.tsx` | 24 | `h-screen w-full` | Flex container de login | `w-full` junto de comportamentos padrão e scrollbars causam scroll horizontal (scroll lateral). |
| `src/pages/Dashboard.tsx` | 234 | `min-h-screen` | Container do Dashboard | Quebra da base de altura no Safari móvel. |
| `src/pages/Board.tsx` | 329, 349 | `h-screen` | Flex wrapper principal | Força rolagem interna e colide com dinâmicas de 100vh em Safari. |
| `src/components/CardModal.tsx` | 403 | `max-h-[90vh]` | Altura de Modal | Comportamento não adaptativo ao teclado virtual (iOS). |
| `src/components/PrivateRoute.tsx`| 8 | `h-screen` | Wrapper de loading | Shift ao transitar para layout sem h-screen. |

## 1.2 Vazamento de Tema (Modo Escriba)
O "Modo Escriba" é um tema pensado para aplicar a paleta específica em *Boards* do tipo *Scribe*. No entanto, está sofrendo vazamento para a aplicação inteira.

- **Origem (Onde definido):** `src/contexts/ThemeContext.tsx`
- **Escopo Desejado:** Apenas dentro de instâncias de visualização de `Board` (Scribe).
- **Escopo Indevido:** Toda a aplicação (Dashboard, Profile, AdminPanel).
- **Causa Raiz:** O Provider de tema (`ThemeContext.tsx`) gerencia o estado `scribeMode` globalmente e realiza injeção direta no root via `document.body.setAttribute("data-scribe-mode", String(scribeMode))`. Adicionalmente, dezenas de componentes (ex: `Profile.tsx`, `AdminPanel.tsx`) consultam ativamente este contexto global e aplicam classes utilitárias condicionalmente (ex: `scribeMode ? 'text-theme-main' : 'text-gray-900'`), acoplando regras de negócio com estilo e quebrando a especificidade.

## 1.3 Layout Shift (CLS)
A aplicação sofre de Cumulative Layout Shift considerável durante as respostas da API do Firebase devido à renderização bloqueante sem reserva visual.

- **Visão Kanban (`Board.tsx` / `KanbanBoard.tsx`):** Dados de listas e cartões não possuem reserva de altura. O estado intermédio apenas contém um texto `Carregando...`, causando o surgimento em bloco dos itens que infla a tela, deslocando posições.
- **Visão Tabela (`TableView.tsx`):** A estrutura nasce sem *Skeletons* de linhas. A passagem de 0 linhas de Skeleton para `n` linhas geradas subitamente quebra a experiência.
- **Visão Calendário (`CalendarView.tsx`):** Células redimensionam abruptamente quando eventos são montados.
- **Estimativa de CLS Atual:** Elevada. A falta de Skeletons (nenhum encontrado no código) e da manutenção da UI Shell implica num redesenho inteiro da DOM.

## 1.4 Acessibilidade Baseline (WCAG 2.2 AA)
Foram identificadas violações flagrantes no que tange os guias essenciais.

- **Landmarks (`<main>`, `<nav>`, `<aside>`):** A maioria das páginas baseia-se unicamente em `<div>` genéricas no lugar de elementos HTML5 semânticos.
- **Atributos ARIA:** Quase nula utilização de atributos `aria-*` para componentes modais (`CardModal.tsx`), menús (`CommandCenter.tsx`) ou alertas. Não há gestão adequada do foco de acessibilidade.
- **Foco Visível e Navegação por Teclado:** Falta de anéis `:focus-visible` nas abstrações de botões customizados para manter consistência sem depender dos padrões imprevisíveis do navegador.

## 2.1 App Shell (Rigid Shell)
O App Shell deve abandonar as diretivas tóxicas (`h-screen`, `100vh`) e passar a usar as medidas de *Dynamic/Small Viewport Height* atreladas às safe-areas nativas. O design utilizará **CSS Grid** para trancar as áreas externas e habilitar rolagem apenas nas áreas internas designadas (`.pt-scroll-area`).

**[PROVENANCE]** (Melhoria de estabilidade mobile | Spec CSS Values 4 & Apple WebKit Blog | Maio 2026)

### Diagrama Mermaid da Rigid Shell
```mermaid
grid
  grid-template-areas:
    "nav   header"
    "nav   main"
  grid-template-columns: 260px 1fr
  grid-template-rows: 64px 1fr
  height: calc(100svh - env(safe-area-inset-bottom))

  "nav" {
    background: var(--color-surface);
    overflow-y: auto; /* .pt-scroll-area */
  }
  "header" {
    background: var(--color-bg);
  }
  "main" {
    background: var(--color-bg);
    overflow: hidden; /* O conteúdo interno lidará com seu próprio scroll */
  }
```
*Em dispositivos móveis, o layout da grid muda para 1 coluna e a navegação se torna um Drawer off-canvas.*

## 2.2 Sistema de Tokens
Com a atualização para **Tailwind CSS v4.2.4**, abandonamos o `tailwind.config.ts` em favor da injeção direta de variáveis via diretiva `@theme` diretamente no arquivo `index.css`.

**Estratégia do Modo Escriba:**
Em vez de vazar classes arbitrárias pelo DOM com ternários, o tema "Scribe" será reduzido a variáveis CSS limitadas ao contexto do componente que hospeda o *Board*. A injeção será feita via `data-theme="scribe"` aplicado **estritamente** na `<div>` raiz do Board, nunca no `document.body`.

**[PROVENANCE]** (Isolamento de estilo e Tailwind v4 CSS-first engine | Tailwind CSS Official Docs | Fev 2026)

**Exemplo de Tokens em CSS:**
```css
@theme {
  --font-mono: 'Space Mono', 'Courier New', monospace; /* Definindo token tipográfico mono */
  
  /* Cores padrão (Base) */
  --color-board-bg: var(--color-slate-50);
  --color-board-text: var(--color-slate-900);
}

/* Scoped Theme: Modo Escriba */
[data-theme="scribe"] {
  --color-board-bg: var(--color-amber-50);
  --color-board-text: var(--color-amber-900);
}
```

## 2.3 Headless Library (Modais / Popovers / Menus)
Para corrigir de forma definitiva os modais sobrepostos e a falta de acessibilidade (Gate 1), precisamos de componentes base que controlem o `z-index`, `focus trap`, e `aria-attributes` de maneira não-opinativa no estilo.

| Critério | Radix UI | Ariakit | Headless UI |
| :--- | :--- | :--- | :--- |
| **WCAG 2.2** | Excelente (Completo) | Excelente (Completo) | Bom |
| **Bundle Size** | Médio (Modular) | Muito Leve | Leve |
| **Atividade do Mantenedor** | Altíssima | Média | Altíssima (Tailwind Labs) |
| **Compat. Tailwind v4** | 100% | 100% | 100% nativa |
| **Gestão Portal/z-index**| Portal Isolado Nativo | Suporte a Portals | Portal Isolado Nativo |

**Recomendação:** **Radix UI Primitives** (ex: `@radix-ui/react-dialog`, `@radix-ui/react-dropdown-menu`).
**[PROVENANCE]** (Padrão ouro de acessibilidade no ecossistema React, arquitetura de portais modularizada que não interfere no Grid do Rigid Shell | Radix UI Docs & W3C ARIA APG | Abril 2026). Portals serão injetados numa div root específica no fim do body `<div id="radix-portal"></div>` para prevenir quebra do App Shell Grid.

## 2.4 Skeletons e Mitigação de CLS
O projeto não tem *Skeletons*. Isso precisa ser implementado para alcançar **CLS < 0.05**.
**[PROVENANCE]** (Core Web Vitals e UX fluída | Google Web.Dev | Março 2026)

- **Visão Kanban (`Board.tsx`):**
  Ao carregar, serão renderizadas 3 colunas "fantasmas" `w-72` com altura de `h-full` (usando background pulsante simulado em Tailwind). Dentro de cada coluna fantasma, 3 *cards* opacos `h-24` para reservar o pixel-equivalent.
- **Visão Tabela (`TableView.tsx`):**
  Renderização imediata dos *Headers* da tabela, seguidos de 10 linhas artificiais simulando a altura base `h-12` da `<tr>`.
- **Visão Calendário (`CalendarView.tsx`):**
  Grid visual estática instantânea, inflando "pastilhas" de Skeleton nos dias correntes.

### 1.4. Categorias de auditoria

#### 1.4.a. Layout / Rigid Shell (cursorrules §1)
- Buscar: `100vw`, `100vh`, `vw`, `vh` em CSS/Tailwind/inline.
- Buscar: `h-screen`, `w-screen`, `min-h-screen`.
- Sinalizar onde `dvh`/`svh`/`lvh` deveriam ser usados.
- Containers que quebrarão com a barra dinâmica do Safari iOS.
- Ausência de `env(safe-area-inset-*)` em PWA.
- Falta de `touch-action: pan-x pan-y` em áreas de scroll.
- Classes globais de tema no `body` (violação §1.4).

#### 1.4.b. Tipagem / Zero-Trust TS (cursorrules §3)
- Localizar: `any`, `unknown` sem narrowing, `as any`.
- Localizar: `@ts-ignore`, `@ts-expect-error` sem justificativa.
- Funções exportadas sem tipo de retorno explícito.
- Uso de `Function`, `Object`, `{}` como tipos.

#### 1.4.c. Segurança / Shadow Logic (cursorrules §2.1)
- Verificações de permissão no frontend sem espelho em
  `firestore.rules`.
- Coleções a auditar: `users`, `boards`, `admin`, `sessions`,
  `billing`, `audit_logs`.
- Itens sem espelhamento = severidade Crítico.

#### 1.4.d. Segurança / XSS (cursorrules §2.2)
- Renderizações de dados do usuário sem `DOMPurify`.
- Uso de `innerHTML`, `dangerouslySetInnerHTML` sem sanitização.
- Sanitização via regex manual (proibida).

#### 1.4.e. Segurança / Data Leakage (cursorrules §2.3)
- Selectors retornando objeto User completo onde 1 campo bastaria.
- E-mails/metadados internos visíveis no frontend.
- Logs do client expondo dados sensíveis.

#### 1.4.f. Segurança / Segredos (cursorrules §2.4)
- `process.env.*` exposto no client bundle.
- Tokens/JWT em `localStorage`/`sessionStorage`.
- Chaves hardcoded em código.

#### 1.4.g. Vibe Coding / Padrões Mortos (cursorrules §8.2)
- `var`, class components React em código novo.
- Lifecycles legados (`componentWillMount`, etc.).
- `moment.js`, `request`, `node-sass`, `enzyme`, jQuery.

#### 1.4.h. Vibe Coding / Antipadrões Memorizados (cursorrules §8.5)
- `try/catch` silencioso (engole erro sem log/throw).
- `JSON.parse` sem guard.
- Regex caseiro para email/URL/CPF.
- `eval`, `Function()` constructor, `setTimeout(string, ...)`.
- `Math.random()` em contexto security-sensitive.
- Comparação de token via `===` (timing attack).

#### 1.4.i. Vibe Coding / Cargo Cult Hooks (cursorrules §8.6)
- `useEffect` para estado derivado calculável.
- `useMemo`/`useCallback` sem profiling que justifique.
- `useState` para constante; `useRef` onde `useState` caberia.

#### 1.4.j. Vibe Coding / Dependências Suspeitas (cursorrules §8.4)
- Pacotes com último release > 12 meses.
- Pacotes com downloads semanais < 10k SEM auditoria documentada.
- Nomes similares a pacotes populares (typosquatting).

#### 1.4.k. Vibe Coding / Falta de Provenance (cursorrules §8.7)
- Decisões arquiteturais não-óbvias sem `// [PROVENANCE] ...`.
- `// TODO: provenance-pending` deixados sem resolução
  (cursorrules §9.2).

## 🔄 ROLLBACK

> ⚠️ Rollback de release publicada é operação delicada. Em
> ambientes que já consumiram a tag, a melhor prática é **avançar
> com hotfix** em vez de reverter. Use os cenários abaixo apenas em
> janela de tempo curta após publicação.

### Cenário A — Antes do push da tag (Etapa 3.6)

Tudo ainda local:

```bash
git tag -d {{TAG_NOME}}
git reset --hard {{BRANCH_BASE}}
git branch -D {{BRANCH_ALVO}}
```

Impacto: zero (nada chegou ao remoto).

### Cenário B — Após push, antes de qualquer deploy

Tag pública mas código não rodando em produção:

```bash
git tag -d {{TAG_NOME}}
git push --delete origin {{TAG_NOME}}
git push --delete origin {{BRANCH_ALVO}}
```

Impacto colateral conhecido:
- Tag deletada do remoto fica visível no histórico de operações git
  do servidor (auditável, esperado).
- Consumidores que clonaram a tag mantêm cópia local (órfã).
- Comunicar imediatamente ao time/stakeholders.

{{#IF_DEPLOY_FIREBASE}}
### Cenário C — Após deploy de rules (mas não código)

Reverter rules ANTES de deletar tag:

```bash
firebase deploy --only firestore:rules --project <project-id>
```

Validar que rules antigas voltaram. Depois aplicar Cenário B.

Impacto:
- Janela curta (segundos) onde rules novas ficaram ativas.
- Auditar logs de acesso nesse intervalo.

### Cenário D — Após deploy completo (rules + código)

Hotfix é preferível a rollback. Se rollback for inevitável:

1. Deploy do código anterior:

```bash
git checkout {{VERSAO_ATUAL}}
firebase deploy --only hosting --project <project-id>
```

2. Deploy das rules anteriores (após código):

```bash
firebase deploy --only firestore:rules --project <project-id>
```

> Atenção: ordem inversa do deploy normal. Aqui o código volta
> primeiro, rules depois, para evitar janela de incompatibilidade.

3. Aplicar Cenário B (delete da tag).

4. Abrir incidente formal e investigar causa raiz.

Impacto colateral:
- Dados criados no intervalo entre deploy e rollback podem ficar
  órfãos ou inconsistentes.
- Auditar `audit_logs` cuidadosamente.
- Considerar comunicação a usuários afetados.
{{/IF_DEPLOY_FIREBASE}}

### Após qualquer rollback

- [ ] Abrir OS de incidente em `docs/orders/` documentando causa.
- [ ] Atualizar `reportStatus.md` com bloco "Rollback {{DATA_UTC}}".
- [ ] Avaliar se itens da auditoria que motivaram a OS revertida
      precisam ser re-priorizados.
- [ ] Não reaplicar a mesma `TAG_NOME` (use `{{TAG_NOME}}-rev1` ou
      similar).

- Landmarks semânticos (`<main>`, `<nav>`, `<header>`).

## 🔄 ROLLBACK

### Cenário A — antes do merge (branch ainda isolada)

```bash
git checkout {{BRANCH_BASE}}
git branch -D {{BRANCH_ALVO}}
git push origin --delete {{BRANCH_ALVO}}
```

Impacto: zero (branch nunca chegou ao código principal).

### Cenário B — após merge (já em branch principal)

```bash
git revert -m 1 <hash-do-merge>
git push
```

Impactos colaterais conhecidos:
- Revert visível no histórico (esperado e auditável).
- Componentes/hooks que dependiam do código revertido podem requerer
  ajuste — abrir OS de remediação se necessário.

{{#IF_TOCA_FIRESTORE_RULES}}
### Cenário C — `firestore.rules` em produção

Se as rules foram deployadas:

```bash
firebase deploy --only firestore:rules --project <project-id>
```

Restaurar versão anterior das rules ANTES de reverter o código, para
evitar janela de inconsistência permission ↔ código.
{{/IF_TOCA_FIRESTORE_RULES}}

### Após qualquer rollback

- [ ] Abrir OS de incidente em `docs/orders/` documentando causa.
- [ ] Atualizar `reportStatus.md` com bloco "Rollback {{DATA_UTC}}".

## 🎯 Sintaxe de Placeholders (Mustache, conforme `prompt.md §3.2`)

### Placeholder simples
```mustache
{{NOME_PARAMETRO}}
```
- Sempre em `UPPER_SNAKE_CASE`.
- Substituído por valor único (string, número, data).

### Lista (seção positiva)
```mustache
{{#LISTA_NOME}}
- {{ITEM}}
{{/LISTA_NOME}}
```
- Usado quando o parâmetro é um array.
- Bloco entre `{{#X}}` e `{{/X}}` é repetido para cada item.

### Condicional positiva
```mustache
{{#IF_TOCA_PRODUCAO}}
ROLLBACK obrigatório
{{/IF_TOCA_PRODUCAO}}
```
- Bloco incluído apenas se a flag for `true`.

### Condicional negativa
```mustache
{{^IF_REQUER_CORRECOES}}
Etapa 2 dispensada nesta OS.
{{/IF_REQUER_CORRECOES}}
```
- Bloco incluído apenas se a flag for `false`.

### Comentário interno
```mustache
{{! este texto não aparece no arquivo final }}
```
- Renderizado como vazio.
- Útil para documentar campos ao revisor humano.

## 🛡️ Regra Inviolável de Validação

Conforme `prompt.md §4`, antes de salvar qualquer OS materializada
em `docs/orders/`, o Antigravity DEVE executar **dois passos** de
validação:

### Passo 1 — Parâmetros não-resolvidos
```regex
\{\{(?![!#/^])[^}]+\}\}
```
Se houver QUALQUER ocorrência → ABORTAR (parâmetro faltando).

### Passo 2 — Seções remanescentes
```regex
\{\{[#/^][^}]+\}\}
```
Se houver QUALQUER ocorrência → ABORTAR (engine Mustache falhou).

> Esta regra impede que arquivos com `{{XYZ}}` literal vazem para o
> repositório, o que constituiria falha de governança ISO 27001/42001.

## 🆘 FAQ

**P: Posso editar um template diretamente sem passar por OS?**
R: Não. Mudanças em template exigem OS de perfil 📘 + ADR.

**P: O que faço se nenhum dos 3 templates estruturados serve?**
R: Use o `prompt-retomada.md` (📐 Livre). Mas reflita: talvez você
esteja diante de um padrão novo que merece um 5º template.

**P: O Oráculo pode propor um template novo?**
R: Pode propor, mas a criação exige sua aprovação + ADR + OS 📘.

**P: E se o Antigravity detectar inconsistência entre OS e cursorrules?**
R: Ele DEVE abortar e reportar antes de executar (ver
`cursorrules.md §10` — Hierarquia de Autoridade).

**P: Como reaproveito uma OS antiga similar?**
R: Não reaproveite o arquivo materializado — refaça o pedido ao
Oráculo apontando a OS antiga como referência. Isso garante que
mudanças no template ou cursorrules sejam incorporadas.

**P: O que faço se o Antigravity declarar incerteza durante uma OS?**
R: Conforme `cursorrules.md §9` e `prompt.md §5`, o Antigravity DEVE
parar e registrar a incerteza no Gate humano mais próximo. Sua
função como PO é decidir: (a) responder a incerteza; (b) abortar a
OS; ou (c) aceitar como hipótese e prosseguir, registrando em
`LISTA_HIPOTESES`.

**P: Por que existe um bloco "Definition of Ready" agora?**
R: Para evitar que OSs entrem em execução com pedido mal-formado. A
DoR força reflexão sobre pré-condições antes da Etapa 0 técnica.
Isso reduz drasticamente o risco de retrabalho.

O artefato mais antigo conhecido de gerenciamento de tarefas analógico no estilo Trello é o Kanban Board (看板), desenvolvido por Taiichi Ohno na Toyota no final dos anos 1940.

Kanban da Toyota (1948–1950)
Ohno criou o sistema para controlar o fluxo de produção nas fábricas da Toyota, inspirado no funcionamento dos supermercados americanos — onde os itens nas prateleiras eram repostos conforme eram consumidos.

O sistema físico original usava cartões de papel (kan = visual, ban = cartão) movidos entre colunas que representavam estágios do trabalho:

[ A FAZER ] → [ EM PROGRESSO ] → [ CONCLUÍDO ]
Cada cartão continha informações sobre a peça ou tarefa, e só era "puxado" para a próxima etapa quando havia capacidade disponível — exatamente a lógica dos cards no Trello.

Existe algo ainda mais antigo?
Sim, de forma mais rudimentar:

Listas de tarefas em argila (Mesopotâmia, ~2000 a.C.) — escribas registravam tarefas e obrigações em tábuas, mas sem o conceito de fluxo entre colunas.
Quadros de produção militares (Primeira Guerra Mundial) — o diagrama de Gantt (1910–1915), de Henry Gantt, é um primo direto: barras horizontais em papel representando tarefas ao longo do tempo.
Mas nenhum deles tinha a mecânica de colunas com cartões móveis que define o estilo Trello. O Kanban da Toyota é o ancestral direto e mais fiel desse modelo.

## 2.4. Como decidir em um Gate

Antigravity vai parar em pontos pré-definidos da OS pedindo decisão.
Existem 3 tipos de Gate por perfil:

### 2.4.a. Gates de implementação (📗)

| Gate | O que Antigravity apresenta | Sua decisão |
|---|---|---|
| Gate 1 | git diff + testes + verificações anti-vibe-coding | ✅ commit OU 🔧 ajustar OU ❌ abortar |
| Gate 2 | git log + push aceito + status CI | ✅ encerrar OS OU ➡️ próxima OS |

### 2.4.b. Gates de governança (📕)

| Gate | O que Antigravity apresenta | Sua decisão |
|---|---|---|
| Gate 1 | Resumo executivo da auditoria + TOP 5 críticos | Decidir quais Críticos: corrigir agora vs aceitar como risco |
| Gate 2 | Correções aplicadas + zero críticos pendentes | ✅ release OU 🔧 ajustar |
| Gate 3 | Commit + tag + push + deploy + smoke tests | ✅ encerrar OS |

### 2.4.c. Gates de doc-sync (📘)

| Gate | O que Antigravity apresenta | Sua decisão |
|---|---|---|
| Gate 1 | git diff dos arquivos docs | ✅ commitar OU 🔧 ajustar |
| Gate 2 | commit + push (+ tag se aplicável) | ✅ encerrar OS |

## 2.5. Quando aprovar vs rejeitar um Gate

```
                  ┌──────────────────────────┐
                  │ Antigravity apresentou   │
                  │ status no Gate           │
                  └──────────────────────────┘
                            │
                            ▼
              ┌───────────────────────────────┐
              │ Tudo prometido foi cumprido?  │
              └───────────────────────────────┘
                            │
              ┌─────────────┴─────────────┐
              SIM                        NÃO
              │                           │
              ▼                           ▼
    ┌──────────────────┐         ┌──────────────────┐
    │ Verifiquei diff  │         │ É falha pequena  │
    │ + lint/test ok?  │         │ corrigível?      │
    └──────────────────┘         └──────────────────┘
              │                           │
       ┌──────┴──────┐             ┌──────┴──────┐
       SIM           NÃO          SIM           NÃO
       │             │             │             │
       ▼             ▼             ▼             ▼
   ✅ APROVAR   🔧 PEDIR        🔧 PEDIR    ❌ ABORTAR
                  PROVA           AJUSTE      a OS
                  EXPLÍCITA
```

### 2.5.a. Sinais de "aprovar com confiança"

- ✅ Diff é exatamente o esperado (não há arquivos extras).
- ✅ Lint + typecheck + test verdes (saída literal mostrada).
- ✅ Antigravity declarou as incertezas honestamente
  (`// TODO: provenance-pending`) e você decidiu sobre cada uma.
- ✅ Zero tokens proibidos no diff.
- ✅ `[PROVENANCE]` presente em decisões não-óbvias.

### 2.5.b. Sinais de "pedir mais prova antes de aprovar"

- ⚠️ Antigravity diz "testes verdes" mas não cola a saída literal.
- ⚠️ Diff mostra arquivos fora da `LISTA_ARQUIVOS_MODIFICAR`.
- ⚠️ Há `// TODO` ou `// FIXME` que não estavam declarados.
- ⚠️ Aparece dependência nova não autorizada.

### 2.5.c. Sinais de "abortar a OS"

- 🚫 Antigravity diz "vou pular validação" ou similar.
- 🚫 Há `any`, `@ts-ignore` introduzidos.
- 🚫 Houve refatoração fora de escopo "porque parecia óbvio".
- 🚫 Auditoria revelou Crítico não-declarado em DoR.
- 🚫 Antigravity ignorou Gate anterior e seguiu sozinho.

> **Princípio:** abortar uma OS **não é fracasso seu**. É evidência
> de que o sistema de governança funcionou. Releases ruins entregues
> são piores do que OSs abortadas.

## 2.6. Quando aceitar risco vs corrigir agora

Em OSs 📕 (governança), o Gate 1 te pede decisão sobre cada item
Crítico encontrado na auditoria. Use a matriz:

```
                  IMPACTO SE FALHAR
                  ┌─────────┬─────────┐
                  │  ALTO   │  BAIXO  │
       ┌──────────┼─────────┼─────────┤
       │  ALTO    │ CORRIGE │ ACEITA  │
EFORÇO │          │  AGORA  │  COM    │
DA     │          │         │ PRAZO   │
CORR.  ├──────────┼─────────┼─────────┤
       │  BAIXO   │ CORRIGE │ CORRIGE │
       │          │  AGORA  │  AGORA  │
       └──────────┴─────────┴─────────┘
```

### 2.6.a. Critérios para "aceitar como risco"

Aceite formalmente como risco APENAS se:

1. ✅ O item NÃO é de segurança crítica (XSS, Shadow Logic, segredos).
2. ✅ O risco está documentado em `BACKLOG.md` com tag
   `[PRIORIDADE: SEGURANÇA]`.
3. ✅ Há prazo declarado para endereçamento (próximo épico, p.ex.).
4. ✅ Você (PO) registra a decisão **por escrito** na OS.

### 2.6.b. NUNCA aceite como risco

- 🚫 Itens de **segurança crítica** (cursorrules §2 inteiro).
- 🚫 Shadow Logic ausente em coleção sensível (`users`, `boards`).
- 🚫 Segredos no client bundle.
- 🚫 XSS em campo de input livre.
- 🚫 `any` em código que toca autenticação/autorização.

> **Regra de ouro:** se a hesitação te dá frio na barriga, **não
> aceite**. Vá para correção agora ou aborte a OS.
